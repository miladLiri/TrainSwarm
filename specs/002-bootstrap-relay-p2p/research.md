# Phase 0 Research: Bootstrap Relay and P2P Communication

## Research Summary

This document evaluates the architectural and protocol design choices for the Bootstrap Relay service, Trainer node architecture, and Client network integration within TrainSwarm.

---

### Decision 1: Bootstrap Relay Web Architecture & Framework

- **Decision**: Implement the Bootstrap service using Python `FastAPI` (with `uvicorn` ASGI server) supported by standard library HTTP server fallback.
- **Rationale**: 
  - FastAPI provides native async support, automatic OpenAPI/Swagger documentation, strict request schema validation via Pydantic/dataclasses, and clean routing.
  - High performance and minimal footprint appropriate for control-plane peer discovery and relay messaging.
- **Alternatives Considered**:
  - *Flask*: Synchronous WSGI, lacks native async routing and automatic OpenAPI schema generation.
  - *Pure `http.server`*: Zero external dependencies, but lacks structured routing, dependency injection, and schema validation.
  - *Custom TCP / Raw Socket Server*: Overly complex for MVP control-plane metadata and relay queueing; violates MVP principle.

---

### Decision 2: DCUtR Peer Relay Messaging Protocol

- **Decision**: HTTP REST inbox/outbox queueing protocol:
  - `POST /api/peers/register`: Node registers its identity (`nodeId`, `role`, `endpoint`) and receives an assigned `peerId` (UUID) and relay address.
  - `GET /api/peers`: Lists active registered swarm peers.
  - `POST /api/relay/send`: Enqueues an opaque payload from `sourcePeerId` to `targetPeerId`.
  - `GET /api/relay/inbox/{peerId}`: Drains queued relayed messages for the requesting peer.
- **Rationale**:
  - Stateless, firewall-friendly, easily inspected, and robust across transient node restarts.
  - Aligns with the clarified decision in `spec.md` (Option A).
  - Provides a clean upgrade path to direct peer-to-peer DCUtR hole-punching in subsequent milestones.
- **Alternatives Considered**:
  - *Persistent WebSocket Streams*: Real-time but requires connection state tracking, heartbeat loops, and reconnection complexity in MVP.
  - *Direct UDP Hole-Punching Only*: Unreliable in strict symmetric NAT environments without a functioning relay fallback.

---

### Decision 3: Presentation-Independent Layering for Trainer Node

- **Decision**: Replicate the exact 4-layer architecture established for Client in Trainer:
  - `domain/`: Business entities and state models (`TrainerNode`, `PeerSession`, `TrainerStatus`).
  - `application/`: Application services and state coordinators (`TrainerState`, `TrainerService`).
  - `infrastructure/`: Network I/O clients (`BootstrapClient`, `CoordinatorClient`).
  - `presentation/`: Interactive console UI and REPL menu loop (`ConsoleUI`).
  - `config.py`: Centralized environment loading via `.env` (`TRAINER_NODE_ID`, `BOOTSTRAP_URL`, `COORDINATOR_URL`).
- **Rationale**:
  - Ensures 100% consistency across data-plane nodes per user requirement and Constitution Principle II.
  - Decouples domain rules from console rendering and transport protocols.
- **Alternatives Considered**:
  - *Monolithic Script*: Rapid to write, but creates tight coupling, untestable logic, and violates Constitution Principle IV.

---

### Decision 4: Peer Identity Model & Lifecycle

- **Decision**:
  - Logical identity: `NodeId` (string from `.env`, e.g., `trainer-node-01`, `client-node-01`).
  - Swarm network identity: `PeerId` (generated by Bootstrap as UUID/string upon registration).
  - Lifecycle: On startup, Trainer and Client ping/register with Bootstrap, store `peerId` in memory, and present it in their interactive console banner.
- **Rationale**:
  - Disambiguates operator-assigned naming (`NodeId`) from transient network session instances (`PeerId`).
  - Allows nodes to restart and receive fresh peer sessions without identity collisions.
- **Alternatives Considered**:
  - *Static Peer IDs*: Operators must manually ensure uniqueness; prone to configuration conflicts.
