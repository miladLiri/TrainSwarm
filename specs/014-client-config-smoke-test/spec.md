# Feature Specification: Training Client Configuration, Dependency Injection, and Smoke Test

**Feature Branch**: `014-client-config-smoke-test`

**Created**: 2026-09-04

**Status**: Draft

**Input**: User description: "Extend the Training Client with three related capabilities: 1. Centralized Configuration Manager for all environment-variable configuration; 2. Lightweight Dependency Injection / Composition Root mechanism for constructing and wiring infrastructure persistence implementations and adapters; 3. Smoke Test application use case that executes a small real training run through the Training Orchestrator, detects training failures before real shards are distributed, measures training throughput, and calculates an appropriate shard sample size from a configured training-time limit."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Centralized Configuration Management and Fast-Fail Validation (Priority: P1)

As a system operator or developer deploying the Training Client, I want all environment-driven configuration centralized in a single Configuration Manager that validates required parameters at startup and parses numeric types, so that misconfigurations or missing settings fail immediately before the application attempts distributed operations.

**Why this priority**: Centralized configuration is the foundation for predictable application startup and runtime stability. Eliminating scattered environment reads is a prerequisite for clean dependency injection and error-free component construction.

**Independent Test**: Instantiate the Configuration Manager in an environment with missing required variables (e.g., missing `COORDINATOR_ADDRESS`), and verify it immediately raises a descriptive configuration error. Then provide valid environment variables (including string paths, numeric timeouts, and shard training time limits) and verify all values are parsed into strongly typed properties.

**Acceptance Scenarios**:

1. **Given** required environment variables (e.g., `COORDINATOR_ADDRESS`) are unset or contain only whitespace, **When** the Configuration Manager initializes, **Then** it raises an explicit configuration validation error identifying the missing variable and prevents application startup.
2. **Given** numeric environment variables (e.g., `REQUEST_TIMEOUT_SECONDS="15.5"`, `SHARD_TRAINING_TIME_LIMIT="300"`), **When** the Configuration Manager initializes, **Then** it parses and exposes them as typed numeric values (`float` or `int`).
3. **Given** an invalid non-numeric string for a numeric configuration variable (e.g., `SHARD_TRAINING_TIME_LIMIT="not-a-number"`), **When** the Configuration Manager initializes, **Then** it raises a type parsing validation error.
4. **Given** optional configuration variables with defaults (e.g., `CLIENT_NODE_ID`, `TRAINING_CLIENT_DB_PATH`, `SHARD_TRAINING_TIME_LIMIT` defaulting to `300.0`, `SHARD_SAFETY_FACTOR` defaulting to `1.0`), **When** those variables are omitted from the environment, **Then** the Configuration Manager populates them with documented, sensible default values.

---

### User Story 2 - Composition Root and Clean Dependency Wiring (Priority: P2)

As a software architect and maintainer, I want a lightweight Composition Root / Dependency Injection mechanism to construct infrastructure adapters, persistence repositories, and application command handlers at the application boundary, so that components receive dependencies explicitly through their constructors without relying on global service locators or third-party frameworks.

**Why this priority**: Explicit dependency wiring decouples business logic from infrastructure implementation details, eliminates hidden global state, and ensures every component can be tested and instantiated in isolation.

**Independent Test**: Execute the composition root container initialization, verifying that `CoordinatorAdapter`, `DatabaseManager`, `TrainingShardRepository`, and `SmokeTestCommandHandler` are constructed with valid configuration and collaborators, while confirming that application classes contain no calls to `container.get` or `container.resolve`.

**Acceptance Scenarios**:

1. **Given** a validated Configuration Manager, **When** the composition root initializes the application graph, **Then** it explicitly constructs infrastructure adapters (passing resolved addresses and timeouts) and persistence instances (passing resolved database paths).
2. **Given** constructed infrastructure and domain components, **When** the composition root wires application command handlers (such as `SmokeTestCommandHandler`), **Then** it injects the required collaborators (`TrainingOrchestrator`, shard training time limit, safety factor) directly into constructor parameters.
3. **Given** any application command handler or domain component, **When** inspecting its implementation and imports, **Then** it has zero dependencies on the DI container and contains no service locator lookups.
4. **Given** existing client infrastructure classes (`CoordinatorAdapter`, `DatabaseManager`), **When** instantiated through the composition root, **Then** they consume explicitly passed constructor arguments without reading environment variables internally.

---

### User Story 3 - Pre-Distribution Training Validation via Smoke Test (Priority: P3)

As a distributed training coordinator, I want to execute a small real training run on a target model and dataset using the Training Orchestrator before partitioning and distributing actual dataset shards, so that training configuration errors, incompatible model architectures, or runtime execution failures are detected early without wasting cluster resources.

**Why this priority**: Sharding and distributing datasets across remote trainers is costly. Detecting bad configurations or broken training loops upfront protects the entire swarm from downstream failure loops.

**Independent Test**: Issue a `SmokeTestCommand` with a valid training task and sample count to `SmokeTestCommandHandler`. Verify that it executes the real `TrainingOrchestrator` on the pre-existing dataset shard in the configured working directory, performs the full training lifecycle on the requested sample count, cleans up generated output delta files, and returns a successful `SmokeTestResult`.

**Acceptance Scenarios**:

1. **Given** a valid `SmokeTestCommand` with `sample_count > 0` and an intact training task referencing a pre-existing dataset shard of `sample_count` samples in the working directory, **When** `SmokeTestCommandHandler.handle(command)` is called, **Then** it invokes the real `TrainingOrchestrator` to execute the validate, prepare, train, and save lifecycle phases without creating temporary sliced artifacts.
2. **Given** a successful smoke test training execution that creates a model delta file in the working directory, **When** the handler completes the run, **Then** it automatically deletes the output delta artifact to prevent disk accumulation.
3. **Given** a training task with invalid hyperparameters, a corrupted model file, or missing dataset files, **When** `SmokeTestCommandHandler.handle(command)` is called, **Then** it catches the failure, logs the diagnostic error details, and returns a `SmokeTestResult` with `success = False` and non-null error information.
4. **Given** a command with `sample_count <= 0`, **When** the handler validates the command, **Then** it rejects the request with a validation error before invoking the training orchestrator.
5. **Given** any smoke test execution, **When** executing training, **Then** it uses the exact same `TrainingOrchestrator` and adapter mechanisms as production training, with zero mock or synthetic training paths.

---

### User Story 4 - Training Throughput Measurement and Shard Sizing Estimation (Priority: P4)

As a dataset partitioning workflow, I want the Smoke Test to measure actual training execution time with high-precision monotonic timing and compute throughput and recommended shard sample capacities, so that real dataset shards can be sized accurately to complete within the configured training time limit.

**Why this priority**: Accurate shard sizing ensures that distributed training workers finish their shards in predictable time windows, preventing worker stragglers and optimizing aggregation cycles.

**Independent Test**: Run a successful smoke test with a known sample count (e.g., 100 samples) and a configured shard training time limit (e.g., 300 seconds). Verify that elapsed monotonic time is recorded in seconds, throughput (`samples_per_second`) is accurately calculated, estimated samples per shard is derived, and recommended samples per shard reflects the configured safety factor.

**Acceptance Scenarios**:

1. **Given** a successful smoke test training run of $N$ samples taking $T$ seconds (where $T > 0$), **When** `SmokeTestCommandHandler` calculates throughput, **Then** it sets `samples_per_second = N / T` in `SmokeTestResult`.
2. **Given** throughput $S$ samples/second and a configured `shard_training_time_limit_seconds` $L$, **When** computing estimated shard size, **Then** it calculates `estimated_samples_per_shard = int(S * L)` and ensures the value is a positive integer.
3. **Given** a configured safety factor $F$ (e.g., 0.8), **When** computing recommended shard size, **Then** it calculates `recommended_samples_per_shard = int(estimated_samples_per_shard * F)`. If no safety factor is configured, `recommended_samples_per_shard` equals `estimated_samples_per_shard`.
4. **Given** an elapsed training time of zero or near-zero, **When** calculating throughput, **Then** the handler treats the measurement as invalid rather than producing infinite or undefined shard sizes.
5. **Given** a failed smoke test run, **When** producing `SmokeTestResult`, **Then** throughput, estimated shard size, and recommended shard size are set to `None`.

### User Story 5 - Client Codebase Migration and Environment Variable Audit (Priority: P5)

As a codebase maintainer, I want all legacy direct environment-variable accesses across `src/Client` audited and migrated to constructor parameters, so that there are no duplicate environment reads or hidden configuration dependencies left in the codebase.

**Why this priority**: Completes the architectural cleanup, enforces the single-responsibility principle for configuration, and ensures the codebase strictly conforms to TrainSwarm architectural standards.

**Independent Test**: Perform an automated codebase scan (e.g. `grep`) across `src/Client` for `os.getenv`, `os.environ`, and `environ.get`. Verify zero occurrences outside the Configuration Manager module. Verify that existing entry points and console interfaces continue to start and run without errors.

**Acceptance Scenarios**:

1. **Given** `src/Client/infrastructure/adapters/coordinator_adapter.py`, **When** inspected, **Then** all direct `os.getenv` calls are removed and `coordinator_address` is strictly a required constructor parameter.
2. **Given** `src/Client/infrastructure/persistence/database.py`, **When** inspected, **Then** all direct `os.getenv` calls are removed and `db_path` is resolved outside the database manager and passed into constructor.
3. **Given** `src/Client/main.py`, **When** executed, **Then** it initializes the Configuration Manager first, passes configuration to the composition root, and starts cleanly.

### Edge Cases

- **Zero or Sub-Millisecond Elapsed Time**: If smoke test training completes in unmeasurably fast time (e.g. 0.0 seconds due to clock granularity or cached operations), the handler must not divide by zero; it must record the issue and mark throughput calculation as invalid.
- **Orchestrator Unhandled Exception**: If `TrainingOrchestrator` raises an unexpected runtime exception (e.g., `OutOfMemoryError`, missing weights file, PyTorch internal error), the handler must catch the exception, log the full traceback, and return `SmokeTestResult(success=False, error=str(e))` without crashing the client.
- **Malformed Numeric Configuration**: If `SHARD_TRAINING_TIME_LIMIT` contains letters, special characters, or negative numbers, Configuration Manager must fail fast during startup validation.
- **Sample Count Exceeding Shard Data**: If requested `sample_count` is larger than the available samples in the referenced dataset shard, the training adapter/orchestrator will raise a validation error, which must be caught and returned as a failed smoke test result.
- **Zero or Negative Safety Factor**: If `SHARD_SAFETY_FACTOR` is set to a value <= 0 or > 1, Configuration Manager must reject it during validation to avoid generating zero or inflated shard sizes.
- **Whitespace-Only Environment Strings**: If an environment variable like `COORDINATOR_ADDRESS="   "` is provided, Configuration Manager must treat it as empty and raise a validation error.
- **Delta Cleanup Permission Failure**: If deleting the generated delta artifact encounters a filesystem permission or locking warning, the handler logs a warning without overwriting or failing a successful `SmokeTestResult`.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST provide a centralized Configuration Manager in `src/Client/config/` as the single authoritative component responsible for reading and parsing environment variables.
- **FR-002**: System MUST prohibit any direct access to environment variables (`os.getenv`, `os.environ`, `os.environ.get`) outside the Configuration Manager across all client modules.
- **FR-003**: Configuration Manager MUST validate all required configuration values (including `COORDINATOR_ADDRESS`) upon initialization and raise an explicit configuration error if any required setting is missing or whitespace.
- **FR-004**: Configuration Manager MUST parse and validate numeric configuration settings (`REQUEST_TIMEOUT_SECONDS`, `SHARD_TRAINING_TIME_LIMIT`, `SHARD_SAFETY_FACTOR`), rejecting non-numeric or non-positive values, while providing documented fallback defaults (including `300.0` seconds for `SHARD_TRAINING_TIME_LIMIT` and `1.0` for `SHARD_SAFETY_FACTOR`) when omitted from the environment.
- **FR-005**: System MUST provide a lightweight Composition Root / Dependency Injection container in `src/Client/dependency_injection/` that constructs and wires infrastructure adapters, persistence implementations, and command handlers.
- **FR-006**: Composition Root MUST construct all dependencies explicitly using constructor injection and MUST NOT use any third-party DI frameworks or global service locator patterns (`container.get` or `container.resolve` in application components).
- **FR-007**: System MUST refactor existing infrastructure constructors (`CoordinatorAdapter`, `DatabaseManager`) to receive their configuration values explicitly through parameters without reading the environment.
- **FR-008**: System MUST provide `SmokeTestCommand` in `src/Client/application/smoke_test/` accepting a `training_task_model` and an integer `sample_count`.
- **FR-009**: System MUST validate that `SmokeTestCommand.sample_count` is an integer strictly greater than zero (`sample_count > 0`), raising a validation error if non-positive.
- **FR-010**: System MUST provide `SmokeTestCommandHandler` in `src/Client/application/smoke_test/` exposing a `handle(command: SmokeTestCommand) -> SmokeTestResult` method.
- **FR-011**: `SmokeTestCommandHandler` MUST receive its dependencies (including `TrainingOrchestrator`, shard training time limit, working directory, and optional safety factor) strictly through constructor injection.
- **FR-012**: `SmokeTestCommandHandler` MUST execute training validation using the existing `TrainingOrchestrator` pointing to the pre-existing dataset shard of `sample_count` samples referenced by `training_task_model` in the configured working directory, without generating temporary sliced artifacts on disk.
- **FR-013**: `SmokeTestCommandHandler` MUST measure the elapsed duration of the training operation in seconds using a monotonic clock (`time.perf_counter()`).
- **FR-014**: System MUST calculate training throughput as `samples_per_second = sample_count / training_time_seconds` when training completes successfully with non-zero elapsed duration.
- **FR-015**: System MUST calculate `estimated_samples_per_shard` by multiplying throughput by `shard_training_time_limit_seconds`, rounded to an integer greater than zero.
- **FR-016**: System MUST calculate `recommended_samples_per_shard` by applying the configured safety factor to `estimated_samples_per_shard`, maintaining distinct values for both fields.
- **FR-017**: System MUST provide `SmokeTestResult` in `src/Client/application/smoke_test/` exposing `success`, `sample_count`, `training_time_seconds`, `samples_per_second`, `shard_training_time_limit_seconds`, `estimated_samples_per_shard`, `recommended_samples_per_shard`, and `error`.
- **FR-018**: When training execution fails, `SmokeTestCommandHandler` MUST log the error context, return a `SmokeTestResult` with `success = False` and non-null `error`, and set all throughput and shard sizing fields to `None`.
- **FR-019**: Smoke test failures MUST be clearly distinguishable from configuration errors and MUST prevent downstream components from treating the training task as validated.
- **FR-020**: System MUST NOT log any sensitive configuration or secrets during configuration loading or error handling.
- **FR-021**: `SmokeTestCommandHandler` MUST automatically delete the output model delta artifact generated by the Training Orchestrator upon smoke test completion to prevent disk accumulation.

### Key Entities

- **ClientConfig**: Centralized immutable configuration object exposing validated, typed properties (`coordinator_address`, `client_node_id`, `request_timeout_seconds`, `db_path`, `shard_training_time_limit_seconds`, `shard_safety_factor`).
- **SmokeTestCommand**: Application command input DTO containing `training_task_model` (the task definition for the orchestrator) and `sample_count` (integer number of samples for the benchmark).
- **SmokeTestResult**: Application command outcome DTO encapsulating validation status, timing measurements, throughput, shard sizing recommendations, and diagnostic error information.
- **DIContainer**: Composition root responsible for assembling the application graph, providing factories or instances of repositories, adapters, and command handlers.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of environment-variable reads in `src/Client` are performed within the Configuration Manager, with exactly 0 occurrences of `os.getenv` or `os.environ` in other client modules.
- **SC-002**: Startup fails with an informative error message in under 500ms when any required environment variable is missing or malformed.
- **SC-003**: 100% of infrastructure adapters and persistence implementations are instantiated via the composition root with explicit constructor arguments.
- **SC-004**: Smoke test execution validates model and dataset compatibility on small sample counts using the real `TrainingOrchestrator`, successfully identifying invalid tasks before shard partitioning.
- **SC-005**: Measured training duration, computed throughput, and estimated shard sample sizes are mathematically consistent with recorded monotonic time and configured time limits.
- **SC-006**: In 100% of training failure scenarios, `SmokeTestResult.success` is `False`, error details are recorded in application logs, and shard size recommendations are suppressed (`None`).
- **SC-007**: Existing Training Client workflows (Coordinator task submission, SQLite shard tracking, console UI startup) continue to function with zero regressions after configuration and constructor refactoring.

## Assumptions

- The Training Client is implemented in Python and runs as a console application within the TrainSwarm architecture.
- The `distributed_training_engine` package and its `TrainingOrchestrator` are available for import within the client execution environment.
- The environment variable for shard training time limit is `SHARD_TRAINING_TIME_LIMIT` (in seconds, defaulting to 300.0), and the safety factor is configured via `SHARD_SAFETY_FACTOR` (defaulting to 1.0).
- The Smoke Test does not create, partition, or persist actual dataset shards; it executes against a pre-existing dataset shard referencing `sample_count` samples in the working directory to produce validation and sizing results for downstream partitioning workflows.
- A monotonic time source (`time.perf_counter()`) is available on all supported deployment operating systems.
