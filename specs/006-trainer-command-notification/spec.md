# Feature Specification: Trainer Command Notification Infrastructure

**Feature Branch**: `006-trainer-command-notification`

**Created**: 2026-08-29

**Status**: Draft

**Input**: User description: "Implement a notification/command infrastructure for communication from the .NET Coordinator to Python Trainers in the distributed training system. This feature is intentionally limited to one-way communication: Coordinator -> Trainer via gRPC. There must be no trainer -> coordinator application-level messaging in this implementation. The underlying gRPC connection must be completely hidden from both the Coordinator application logic and Trainer application/training logic. The infrastructure must be designed so additional command types and handlers can be added later without modifying the underlying transport or existing application architecture."

## Clarifications

### Session 2026-08-29
- Q: How should the Trainer establish the long-lived command stream with the Coordinator in the gRPC service definition? → A: Server-streaming RPC (`rpc SubscribeCommands(TrainerRegistrationRequest) returns (stream CommandEnvelope)`) passing `trainerId` in the initial registration request message.
- Q: What method signature and failure behavior should the Coordinator's `ICommandCenter.SendAsync` abstraction use when the target Trainer is not connected? → A: Return a detailed result object (`Task<CommandDispatchResult> SendAsync(...)`) containing success flag, command ID, and failure reason.
- Q: How should the Python Trainer execute command handlers when a command is dispatched? → A: Each command handler implementation decides its own execution model (synchronous or background/async) independently.
- Q: What retry and backoff strategy should the Trainer transport use when reconnecting to the Coordinator? → A: Fixed interval retry (attempt reconnection every 5 seconds).
- Q: How should the command payload `data` field be represented in the protobuf `CommandEnvelope` definition? → A: UTF-8 JSON string (`string data = 3`) holding the raw serialized JSON payload of the command.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Coordinator Dispatches StartTraining Command to Connected Trainer (Priority: P1)

As the Coordinator application, I want to send a strongly typed `StartTraining` command to a specific connected Trainer via a high-level Command Center abstraction, so that the target Trainer receives the session and client details necessary to begin training without exposing gRPC transport mechanics to application logic.

**Why this priority**: Establishing the one-way command transport and successfully delivering `StartTraining` is the core capability required to orchestrate training execution across the swarm.

**Independent Test**: Can be tested by starting the Coordinator service, launching a Trainer that establishes a long-lived command stream with its `trainerId`, invoking `CommandCenter.SendAsync(trainerId, startTrainingCommand)` from Coordinator application code, and verifying that the Trainer's `StartTrainingHandler` receives the fully deserialized, strongly typed `StartTrainingCommand` containing `trainingClientNodeId` and `sessionId`.

**Acceptance Scenarios**:

1. **Given** the Coordinator service is running and a Trainer identified as `"trainer-node-01"` has established an active command stream, **When** Coordinator application logic issues a `StartTraining` command for `"trainer-node-01"` with `trainingClientNodeId: "node-123"` and `sessionId: "session-456"`, **Then** the Coordinator Command Center wraps the command in a common envelope with a unique `id`, `type: "StartTraining"`, serializes `data`, transmits it over the gRPC stream to `"trainer-node-01"`, and the Trainer's `StartTrainingHandler` is invoked with the typed command model.
2. **Given** a command is sent, **When** the message envelope is generated by the Coordinator, **Then** it contains a non-empty unique string identifier (`id`), the string/enum representation of the command type (`type: "StartTraining"`), and the serialized payload (`data`).

---

### User Story 2 - Extensible Trainer Command Dispatching and Typed Handling (Priority: P2)

As a Trainer developer, I want incoming command envelopes to be parsed and routed by a generic command dispatcher to modular, typed handlers without modifying gRPC transport code, so that new command types can be introduced or existing handlers replaced seamlessly.

**Why this priority**: Future command types (e.g., Pause, Stop, Checkpoint) will be introduced. Decoupling transport from command dispatching prevents regression and architectural drift.

**Independent Test**: Can be tested by registering a new command type and handler with the Trainer's dispatcher registry, sending a corresponding command envelope from the Coordinator, and verifying the new handler is executed with typed arguments without modifying gRPC service or stream handling code.

**Acceptance Scenarios**:

1. **Given** a command envelope arrives at the Trainer over the gRPC stream, **When** the generic Command Dispatcher inspects `type`, **Then** it resolves the registered handler for that `type`, deserializes `data` into the corresponding typed command class, and executes the handler.
2. **Given** a command handler implementation is swapped or modified (e.g., custom `StartTrainingHandler`), **When** the Trainer is initialized with the updated handler, **Then** commands are dispatched to the updated handler without requiring changes to gRPC transport or stream lifecycle components.

---

### User Story 3 - Connection Lifecycle, Identification, and Reconnection (Priority: P3)

As a Trainer node operator, I want my Trainer application to establish a persistent connection with the Coordinator at startup using its unique identity and automatically re-establish that connection if the stream drops, so that the Coordinator can reliably route commands to my node across network disruptions.

**Why this priority**: Distributed nodes operate over variable network connections; connection establishment and recovery must be self-healing and managed transparently by the transport layer.

**Independent Test**: Can be tested by starting a Trainer, confirming connection registration in the Coordinator, severing the network connection or restarting the Coordinator, and verifying the Trainer reconnects using the same `trainerId` while the Coordinator updates its active connection map to the new stream.

**Acceptance Scenarios**:

1. **Given** a Trainer application starts with a configured `trainerId`, **When** the Trainer initializes its connection transport, **Then** it opens a long-lived gRPC connection to the Coordinator and provides its `trainerId` during connection establishment without requiring a separate registration API call.
2. **Given** an existing Trainer with `trainerId: "trainer-01"` reconnects after a disconnect, **When** the new connection is established, **Then** the Coordinator associates `"trainer-01"` with the new active connection, cleans up the old connection state, and routes subsequent commands to the new stream.

---

### User Story 4 - Resilient Command Routing and Error Handling (Priority: P4)

As a Coordinator and Trainer operator, I want the system to handle missing targets, unknown command types, and malformed payloads gracefully with clear error reporting and logging, so that invalid messages or network anomalies do not crash either service.

**Why this priority**: System stability requires defensive message processing and clear diagnostics when commands fail to deliver or deserialize.

**Independent Test**: Can be tested by sending a command to an unregistered `trainerId` from the Coordinator, and by injecting an unknown command `type` or malformed `data` into the Trainer's stream, verifying that appropriate exceptions/logs are produced without process termination.

**Acceptance Scenarios**:

1. **Given** the Coordinator attempts to send a command to a `trainerId` that has no active connection, **When** `CommandCenter.SendAsync` is called, **Then** it raises or returns an explicit connection unavailable indication rather than silently discarding the command.
2. **Given** a message envelope with an unrecognized `type` or invalid `data` payload reaches the Trainer, **When** the Command Dispatcher processes the message, **Then** the dispatcher logs an observable error, skips execution safely, and remains open to receive subsequent commands without crashing.

---

### Edge Cases

- **Target Trainer Disconnected / Unavailable**: When a command is targeted at a Trainer with no active connection, the Coordinator's Command Center fails fast with a designated transport/connection exception or status, logging the unroutable command ID and target `trainerId`. No offline queueing is performed in this phase.
- **Malformed Message Envelope / JSON Parsing Error**: If a corrupted or unparseable JSON payload is received by the Trainer, the transport/dispatcher catches the deserialization error, logs the failure with the raw envelope details, and keeps the stream active for future messages.
- **Unknown Command Type**: If a command arrives with an unrecognized `type` enum value (e.g., from a newer Coordinator version), the Trainer dispatcher logs an unknown-type warning and safely ignores the payload without crashing.
- **Invalid Payload for Known Type**: If the `type` is known (e.g., `StartTraining`) but required fields (`trainingClientNodeId` or `sessionId`) are missing or of incorrect types, deserialization validation fails, an error is logged, and the specific handler is not invoked.
- **Trainer Re-registration / Rapid Reconnect**: If a Trainer connects with a `trainerId` that already has an open stream (e.g., due to stale socket or rapid restart), the Coordinator replaces the active connection mapping with the newly established stream and releases resources for the old stream.
- **Stream Termination Mid-Command**: If the gRPC connection drops while a command is being transmitted, the Coordinator transport layer detects the stream write failure, cleans up the active connection association, and reports the transport failure to the caller.

## Requirements *(mandatory)*

### Functional Requirements

#### Protocol & Shared Contract

- **FR-001**: The communication protocol MUST be strictly one-way from Coordinator to Trainer over a long-lived gRPC streaming connection. No Trainer-to-Coordinator application-level messaging, acknowledgements, progress reporting, or heartbeats shall be implemented in this feature.
- **FR-002**: Every command transmitted over the transport MUST be encapsulated in a common protobuf `CommandEnvelope` containing:
  - `id`: Unique string identifier generated by the Coordinator for the message (`string id = 1`).
  - `type`: String representation of a strongly typed `CommandType` enum (`string type = 2`).
  - `data`: UTF-8 JSON string containing the command-specific payload (`string data = 3`).
- **FR-003**: The .NET Coordinator and Python Trainer MUST implement identical field naming, capitalization (camelCase in JSON serialization), structure, and semantics for the shared envelope and command payloads.
- **FR-004**: The system MUST define a `CommandType` enum implemented consistently across .NET and Python, with the initial supported value `StartTraining`.
- **FR-005**: The system MUST implement the `StartTraining` command payload containing:
  - `trainingClientNodeId`: String representing the client node owning the training session.
  - `sessionId`: String representing the unique session identifier.

#### Coordinator Architecture (.NET)

- **FR-006**: The Coordinator MUST expose an application-facing `ICommandCenter` abstraction returning a structured `Task<CommandDispatchResult> SendAsync(string trainerId, CommandType type, object commandData)` and typed generic overload `Task<CommandDispatchResult> SendAsync<T>(string trainerId, T command)`.
- **FR-007**: Coordinator application logic MUST NOT interact directly with gRPC clients, gRPC streaming calls, socket connections, or JSON serialization primitives.
- **FR-008**: The Coordinator `CommandCenter` MUST be responsible for generating unique message IDs, wrapping commands into the `CommandEnvelope`, serializing payloads to JSON, resolving the active connection for the target `trainerId`, and delegating transmission to the transport layer.
- **FR-009**: The Coordinator MUST implement a `TrainerConnectionManager` that maintains an in-memory mapping of `trainerId` to active gRPC stream connections.
- **FR-010**: Connection establishment from a Trainer MUST supply the `trainerId` as part of the initial connection registration message via the server-streaming gRPC method `SubscribeCommands(TrainerRegistrationRequest) returns (stream CommandEnvelope)` without requiring a separate registration API call.
- **FR-011**: When a new connection is established for an existing `trainerId`, the `TrainerConnectionManager` MUST update the active connection mapping to the new connection and release the prior stream.
- **FR-012**: When a connection/stream is terminated or closed, the `TrainerConnectionManager` MUST detect the closure and remove the connection from the active mapping.
- **FR-013**: If a command is sent to a `trainerId` that is not currently connected or if transport write fails, `ICommandCenter.SendAsync` MUST return a `CommandDispatchResult` with `IsSuccess = false`, the generated command ID, and a descriptive error reason (e.g. `TrainerNotConnected` or `TransportError`) without silent message drops.

#### Trainer Architecture (Python)

- **FR-014**: The Trainer application MUST establish a long-lived gRPC command stream to the Coordinator upon startup, transmitting its configured `trainerId` during connection initialization.
- **FR-015**: The Trainer application and training logic MUST NOT have any direct dependency on gRPC channels, stubs, streams, or connection lifecycle events.
- **FR-016**: The Trainer MUST implement a generic `CommandDispatcher` that sits between the gRPC transport and command handlers.
- **FR-017**: The `CommandDispatcher` MUST inspect the envelope `type`, resolve the registered handler for that type, deserialize the `data` JSON object into a strongly typed command model (e.g., `StartTrainingCommand`), and invoke the handler.
- **FR-018**: Each command type MUST be handled by a dedicated handler implementing a common `ICommandHandler` interface or contract. Each handler implementation decides its own internal execution strategy (synchronous or spawning a background thread/task).
- **FR-019**: The `StartTrainingHandler` MUST receive a strongly typed `StartTrainingCommand` object and invoke the appropriate application/training logic.
- **FR-020**: The `CommandDispatcher` MUST support dynamic or dependency-injected registration of handlers so that new command types and handlers can be added without modifying the gRPC transport or dispatcher infrastructure.
- **FR-021**: The Trainer transport layer MUST detect stream disconnections and attempt reconnection using the existing `trainerId` with a fixed interval retry of 5 seconds to restore command reception.

#### Error Handling & Observability

- **FR-022**: The system MUST distinguish between transport-level errors (stream closed, network failure), envelope/parsing errors (malformed JSON), routing errors (target trainer offline, unknown command type), and application handler errors.
- **FR-023**: Unknown command types received by the Trainer MUST be logged with an observable warning and discarded safely without interrupting stream processing or crashing the process.
- **FR-024**: Deserialization failures of command payloads MUST be logged with error details and MUST NOT invoke the corresponding handler.
- **FR-025**: The Coordinator and Trainer MUST log critical lifecycle and message events including:
  - Trainer connection opened / closed with `trainerId`.
  - Command dispatched with `id`, `trainerId`, and `type`.
  - Command received with `id` and `type`.
  - Deserialization and handler execution failures.

### Key Entities *(include if feature involves data)*

- **CommandEnvelope**: The root protobuf message container transmitted over gRPC streams.
  - Attributes: `id` (string UUID), `type` (enum / string name of command), `data` (UTF-8 JSON string containing command-specific payload).
- **CommandDispatchResult**: Coordinator-side result model returned by `ICommandCenter.SendAsync`.
  - Attributes: `isSuccess` (boolean), `commandId` (string UUID), `errorMessage` / `failureReason` (string, optional).
- **CommandType**: Enumeration of supported command types across Coordinator and Trainer.
  - Values: `StartTraining`.
- **StartTrainingCommand**: Strongly typed payload model for initiating a training session on a Trainer.
  - Attributes: `trainingClientNodeId` (string), `sessionId` (string).
- **TrainerConnection**: Coordinator-side representation of an active long-lived connection stream associated with a specific Trainer.
  - Attributes: `trainerId` (string), `connectedAt` (timestamp), `streamWriter` (gRPC response stream handle).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of valid commands dispatched from the Coordinator `ICommandCenter` to an active Trainer are received and mapped to their typed handler with complete data fidelity.
- **SC-002**: Trainer application and training logic contain zero imports or references to gRPC packages, stubs, or transport primitives.
- **SC-003**: Adding a new command type requires zero changes to the underlying gRPC transport or connection management code on either Coordinator or Trainer.
- **SC-004**: If a Trainer disconnects and reconnects with the same `trainerId`, subsequent commands are successfully delivered to the new connection stream within 1 second of reconnection.
- **SC-005**: 100% of malformed payloads and unrecognized command types are safely caught and logged without causing unhandled exceptions, stream termination, or process crashes in the Trainer.
- **SC-006**: When targeting an offline Trainer, the Coordinator Command Center detects the absence of an active connection and surfaces an explicit failure within 50 milliseconds without deadlocks or timeouts.

## Assumptions

- The .NET Coordinator hosts the gRPC server endpoint, and Python Trainers act as gRPC clients initiating outgoing connections to the Coordinator.
- Each Trainer has a configured, stable `trainerId` provided via environment variables or configuration at startup.
- Transport reliability relies on the underlying HTTP/2 / gRPC stream; no application-level ACK or persistent offline queue is implemented in this phase.
- Command payloads are serialized to JSON using standard camelCase naming conventions across both .NET (`System.Text.Json`) and Python (`json` / `dataclasses` / `pydantic`).
- Out-of-band communication (e.g., training metrics, completion results) will be handled separately via Client-Trainer P2P or existing REST endpoints and is outside the scope of this one-way command infrastructure.
