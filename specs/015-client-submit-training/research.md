## Technical Context & Research Objectives

The objective of this research phase is to establish clear architectural decisions, file layout patterns, state transition rules, and dependency boundaries for:
1. End-to-end training task submission (`SubmitTrainingCommand`, `SubmitTrainingCommandHandler`, `SubmitTrainingResult`).
2. Artifact staging and smoke test working directory scoping.
3. Shard lifecycle management in SQLite (`CREATED` and `READY`).
4. Dual presentation layer: non-interactive CLI flags in `ConsoleUI` and a decoupled desktop GUI in `src/Client/presentation/gui/` using PyQt6.
5. Packaging and headless Docker execution (`requirements.txt` vs `requirements-gui.txt`, `/artifacts` volume).
6. End-to-end verification sample suite in `samples/submit_training_test/`.

## Research Decisions

### 1. Artifact Staging, Scoping, and Smoke Test Isolation

- **Decision**: When `SubmitTrainingCommandHandler.handle()` executes, it generates UUIDs for `model_id` and `dataset_id`. It creates a dedicated directory `{working_directory}/{model_id}/` and stages the model checkpoint as `{model_id}_{model_version}.pt2`. The training configuration JSON is written beside it as `{model_id}_{model_version}_config.json`.
- **Smoke Test Scoping**: The handler configures `PartitioningOrchestrator` to extract the representative sample into `{working_directory}/{model_id}/{dataset_id}_sample.pt`. The `SmokeTestCommandHandler` executes with `working_directory = {working_directory}/{model_id}`, matching `CanonicalTorchTrainer` path resolution expectations (`{working_directory}/{baseline_model_id}_{baseline_model_version}.pt2` and `{working_directory}/{data_set_id}_{data_set_shard_id}.pt`).
- **Cleanup**: The temporary sample file `{working_directory}/{model_id}/{dataset_id}_sample.pt` is unconditionally deleted upon smoke test completion.
- **Partitioning Destination**: Shards generated from `PartitioningOrchestrator.create_shards()` are written to `{working_directory}/shards/{dataset_id}/`.
- **Alternatives Considered**:
  - *Staging in client root working directory*: Rejected because multiple submissions or concurrent model versions would collide and clutter the root directory.
  - *Symlinking checkpoint*: Rejected because Windows environments without developer mode restrict non-elevated symlink creation; file copying provides deterministic cross-platform reliability.

### 2. Shard Lifecycle Status & Atomic Persistence in SQLite

- **Decision**: Extend `TrainingShardStatus` enum in `src/Client/domain/training_shard.py` with `CREATED = "created"`. Add `update_status(shard_ids: List[str], status: TrainingShardStatus) -> None` to `ITrainingShardRepository` and `TrainingShardRepository`.
- **Persistence Sequence**:
  1. Shards generated by `PartitioningOrchestrator` are instantiated as `TrainingShard` domain models with `status = TrainingShardStatus.CREATED`.
  2. The handler persists shards using `TrainingShardRepository.bulk_save(shards)`.
  3. The handler submits `CreateTrainingTaskDto` to the Coordinator via `CoordinatorAdapter.create_training_task()`.
  4. Upon receiving `trainingTaskIds`, the handler invokes `TrainingShardRepository.update_status(shard_ids, TrainingShardStatus.READY)`.
  5. If the Coordinator call fails or times out, the records remain in SQLite with status `CREATED`.
- **Atomic Transaction**: `update_status` executes inside `BEGIN IMMEDIATE` with parameter substitution `UPDATE training_shards SET status = ? WHERE id IN (...)` ensuring zero torn state.
- **Alternatives Considered**:
  - *Saving directly as READY*: Rejected because if the Coordinator call times out or fails, the database would falsely record unassigned shards as ready for swarm training.
  - *Deleting local shards on Coordinator error*: Rejected because partitioned shard files on disk would become untracked orphans; retaining `CREATED` status allows recovery or retry.

### 3. Application Command & Composition Root Wiring

- **Decision**: Implement `SubmitTrainingCommand`, `SubmitTrainingCommandHandler`, and `SubmitTrainingResult` under `src/Client/application/submit_training/`.
- **Dependencies**: `SubmitTrainingCommandHandler` receives its dependencies strictly through constructor injection:
  - `working_directory: Path`
  - `smoke_test_handler: SmokeTestCommandHandler`
  - `shard_repository: ITrainingShardRepository`
  - `coordinator_adapter: Optional[CoordinatorAdapter]`
  - `client_node_id: str`
- **Wiring in `DIContainer`**:
  Add property `submit_training_handler` to `DIContainer` in `src/Client/dependency_injection/container.py`, cleanly constructing it using existing container components.
- **Alternatives Considered**:
  - *Direct instantiation in CLI / GUI*: Rejected because it violates Dependency Inversion and bypasses the Composition Root.

### 4. Dual Presentation: CLI and PyQt6 Desktop GUI

- **CLI (`src/Client/presentation/console_ui.py` & `main.py`)**:
  - Standard `argparse` parser handles subcommand `submit-training` with flags:
    - `--model-path <path>` (required)
    - `--dataset-path <path>` (required)
    - `--model-version <version>` (required)
    - `--model-type <type>` (defaults to `canonical_torch`)
    - `--training-config <path.json>` (required)
  - Outputs real-time progress steps and returns exit code 0 on success or 1 on failure.
- **PyQt6 GUI (`src/Client/presentation/gui/`)**:
  - Located under `src/Client/presentation/gui/`.
  - Architecture: Model-View-Presenter (MVP). The view (`MainWindow`) defines UI components; the presenter/controller handles command construction and dispatches to a background `QThread` worker (`SubmitTrainingWorker`).
  - Tabs:
    - **Submit Training Tab**: File pickers (model `.pt2`, dataset `.pt`), version input, model type dropdown, scheduler dropdown, optimizer inputs, batch size/epochs spinboxes, Submit button, inline progress bar, and status phase banner.
    - **Logs Tab**: Read-only text area with timestamped log streaming and clear button.
  - UI isolation: The main thread handles events and user interaction; the background worker handles file operations, smoke testing, partitioning, and networking, communicating via PyQt signals (`progress_updated`, `log_emitted`, `finished`, `failed`).
- **Alternatives Considered**:
  - *Single tab GUI*: Rejected because separating submission controls from verbose log inspection maintains a clean, modern layout.
  - *Synchronous UI execution*: Rejected because heavy autograd training in smoke test would freeze the desktop interface and cause OS warnings.

### 5. Packaging, Dependencies, and Headless Docker Separation

- **Decision**:
  - Core [`requirements.txt`](file:///C:/Users/azure-dev/dev/TrainSwarm/src/Client/requirements.txt): Contains `requests>=2.31.0`, `python-dotenv>=1.0.0`, `torch>=2.2.0`, `safetensors`. This allows headless CLI and Docker containers to run training without graphical libraries.
  - Desktop [`requirements-gui.txt`](file:///C:/Users/azure-dev/dev/TrainSwarm/src/Client): Contains `PyQt6>=6.6.0`.
  - Dockerfile: Installs `requirements.txt`, declares `VOLUME ["/data", "/artifacts"]`, sets `ENV TRAINING_CLIENT_WORKING_DIRECTORY=/artifacts`, and runs `python main.py`.
- **Alternatives Considered**:
  - *Including PyQt6 in core requirements*: Rejected because Linux Docker images would require extensive X11/GL libraries and balloon image sizes for a headless environment.

### 6. End-to-End Verification Test Sample (`samples/submit_training_test/`)

- **Decision**: Implement a self-contained test directory with three scripts:
  - `setup.py`: Provisions Docker network `trainswarm-test-net`, launches Coordinator and Client containers with volume mount `./artifacts:/artifacts`, checks HTTP `/health` on Coordinator, and verifies connectivity.
  - `clean.py`: Stops and removes test containers, removes Docker network, and deletes local `./artifacts` test outputs.
  - `e2e-test.py`: Synthesizes dynamic test models (`.pt2`) and datasets (`.pt`) into `./artifacts`, runs `docker exec` against the Client container CLI across 5 test paths (happy path, invalid model, invalid dataset format, malformed config, coordinator outage), and formats output in a clean, readable pass/fail table.
- **Alternatives Considered**:
  - *Running tests on host*: Rejected because the user explicitly requested containerized verification connecting Coordinator and Client via Docker.
